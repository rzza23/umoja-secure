# artifacts/

Build-artifact snapshots for review. Not source code.

Tracked files are refreshed only when the underlying lockfile changes.
Spurious refresh noise defeats the purpose of having a git history of
these files.

## dep-tree.json

Generated by:
  cd backend && python3 ../scripts/ci/regen-dep-tree.py

The tree carries a `_meta` block with:
  - lockfile_sha: sha256 of backend/package-lock.json at generation time
  - schema: "umoja-dep-tree.v1"
  - generated_at_utc: ISO 8601 timestamp
  - generated_by: "scripts/ci/regen-dep-tree.py"

check-dep-tree-refresh.py verifies _meta.lockfile_sha against the
current lockfile. Regenerate whenever backend/package-lock.json
changes; the hash check catches a lockfile update without a
corresponding regen.

The tree uses `npm ls --omit=optional` internally so that optional,
os-constrained deps (fsevents on macOS, per-platform esbuild binaries)
don't appear. Those deps legitimately differ by platform. §11
enforcement (no Google runtime packages) is handled by the SBOM check
(check-prohibited.py), which includes optional deps for absolute
enforcement.

Per Build Master section 6, every PR should include a fresh
dep-tree.json reviewed for:
  - @google/*, com.google.*, googleapis, gaxios,
    google-auth-library, firebase*, tink (runtime deps only)
  - Any package without a resolved version
  - Any package newly added in the PR

Refresh this file when backend/package-lock.json changes. Do not
refresh on every `npm install` if the lockfile is unchanged -- the
dep-tree is deterministic for a fixed lockfile.

## dep-tree-android.json

Generated by:
  cd android && python3 ../scripts/ci/regen-dep-tree-android.py

The tree carries a `_meta` block with:
  - lockfile_sha: sha256 over the three gradle input files, in order:
    android/gradle/libs.versions.toml
    android/app/build.gradle.kts
    android/settings.gradle.kts
    concatenated with "\n---\n" separators. See
    scripts/ci/gradle_lockfile_sha.py for the exact composition and
    rationale -- the project does not use Gradle dependencyLocking,
    so there is no single lockfile to key on.
  - lockfile_files: the three files, in the order they were hashed
  - schema: "umoja-dep-tree-android.v1"
  - configuration: "clientReleaseRuntimeClasspath" (the flavor-
    qualified classpath that reaches a user device)
  - generated_at_utc: ISO 8601 timestamp
  - generated_by: "scripts/ci/regen-dep-tree-android.py"

check-dep-tree-refresh-android.py verifies _meta.lockfile_sha against
the current gradle inputs. Regenerate whenever any of the three input
files changes; the hash check catches an input update without a
corresponding regen.

Unlike backend/dep-tree.json, this tree is parsed directly for §11
enforcement. There is no Android SBOM: ADR-CI-GATE-001 §9 out-scopes
full Android SBOM generation, so the dependency tree is the
enforcement surface (check-prohibited-android.py reads it). Versions
that ship in the release APK are all present here; dev/test-only deps
are not (clientReleaseRuntimeClasspath excludes testImplementation
and androidTestImplementation).

Why clientReleaseRuntimeClasspath: the client/signing flavor split
landed at Session Z-17. There is no flavor-agnostic runtime classpath.
The client flavor ships the user app, so it is the §11 enforcement
surface. The signing flavor ships only to ceremony devices (air-
gapped, no network, no user data) and is not part of the user-device
threat model.

The two active §2 carve-outs that fire on this tree:
  - com.google.zxing:core@3.4.1
    (transitive from journeyapps:zxing-android-embedded:4.3.0)
  - com.google.guava:listenablefuture@1.0
    (transitive from androidx.concurrent:concurrent-futures:1.1.0
    via androidx.core:core:1.16.0 and the Compose BOM)

Both are interface-only or community artifacts under historical
com.google.* groupIds. See DEPENDENCY-EXCEPTIONS.md §2 for the §8.1
clearance reasoning.

Per Build Master section 6, every PR should include a fresh
dep-tree-android.json reviewed against the same §11 list the backend
gate enforces. Refresh only when a gradle input changes -- the tree
is deterministic for fixed inputs.

## What does NOT belong here

- sbom.json -- gitignored in both repo-root and backend/ .gitignore;
  generated on demand for review, not committed
- Any Android SBOM -- out of scope per ADR-CI-GATE-001 §9. The tree
  in dep-tree-android.json is the Android enforcement surface.
- Any file that contains credentials, tokens, or environment-specific
  paths
- Build outputs (dist/, build/, node_modules/) -- gitignored by
  convention
